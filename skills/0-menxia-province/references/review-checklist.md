# 审核清单

**门下省各阶段审核的详细检查清单。**

---

## 阶段 1：需求审核

### 必查项

- [ ] 需求文档是否存在于 `.cache/shared/requirements/`
- [ ] 是否覆盖皇上旨意的所有需求点（逐条对照）
- [ ] 每个功能点是否有对应的用户故事
- [ ] 用户故事格式：作为{角色}，我想要{功能}，以便{价值}
- [ ] 每个用户故事是否有明确的验收标准
- [ ] 异常场景和边界条件是否已考虑
- [ ] 需求之间是否有矛盾或冲突

### 建议查项

- [ ] 非功能需求（性能、安全、兼容性）是否明确
- [ ] 需求优先级是否合理
- [ ] 是否有遗漏的隐含需求

## 阶段 2：架构审核

### 必查项

- [ ] 架构设计文档是否存在于 `.cache/shared/architecture/`
- [ ] 技术选型是否合理（与项目现有技术栈兼容）
- [ ] 模块划分是否清晰，职责是否单一
- [ ] 数据模型是否完整，字段类型是否正确
- [ ] API 设计是否符合 RESTful 规范
- [ ] 是否有安全风险（SQL注入、XSS、CSRF等）
- [ ] 是否有性能瓶颈（N+1查询、大数据量处理等）

### 建议查项

- [ ] 是否考虑了扩展性
- [ ] 是否考虑了向后兼容
- [ ] 外部依赖是否最小化

## 阶段 3：代码审核

### 必查项

- [ ] 代码是否实现了需求文档中的所有功能点
- [ ] 单个文件是否 ≤ 800 行
- [ ] 单个方法是否 ≤ 50 行
- [ ] 是否有 OWASP Top 10 安全漏洞
- [ ] 是否有硬编码的密钥、密码、token
- [ ] 代码是否通过 Agent 子进程编写（三省六部模式强制要求）
- [ ] 是否有对应的测试用例

### 建议查项

- [ ] 代码是否遵循 KISS 原则
- [ ] 是否有重复代码可以抽取
- [ ] 命名是否清晰有意义
- [ ] 注释是否必要且准确

## 审核评分标准

| 等级 | 说明 | 决策 |
|---|---|---|
| A | 所有必查项通过，建议项大部分通过 | 准奏 |
| B | 所有必查项通过，建议项部分未通过 | 准奏（附建议） |
| C | 1-2 个必查项未通过 | 封驳 |
| D | 3 个以上必查项未通过 | 封驳（严重） |
