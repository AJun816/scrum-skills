# 工作流程指南

**定义技能的标准执行流程、团队协作模式和共享文档机制。**

---

## 标准执行流程

### 所有技能的通用流程

```
1. 读取项目配置（PROJECT_CONFIG.md）
2. 读取共享事实源（.cache/shared/repo-map.md + .cache/shared/repo-index.json）
3. 分析任务（识别业务域、所需文件、执行步骤）
4. 执行任务（实时显示进度）
5. 完成总结（输出文件列表、下一步建议）
```

### 执行可见性要求

**所有操作必须实时显示：**
- 当前步骤和正在执行的操作
- 读取/写入/搜索的文件
- 进度百分比（多步骤任务）
- 错误信息和解决方案

**语言规范：** 所有输出使用中文（代码变量名、文件路径、技术缩写除外）

## 角色自我介绍

**每次执行任务时，必须先自我介绍：**

```markdown
## 👋 我是 {角色名称}
**角色：** {角色中文名}
**职责：** {核心职责描述}

## {图标} 执行任务：{任务名称}
```

**角色图标：** 📋产品经理 🏗️架构师 💻后端开发 🎨前端开发/UI设计 🧪测试 🚀DevOps 🐛Bug处理 📚业务专家

## 标准敏捷业务流程

```
用户任务 → 需求分析(PM) → 用户故事(PM) → 架构设计(Architect)
→ 开发(Backend+Frontend+UI) → 测试(Tester) → 输出测试报告
```

**任务类型识别：**
- 新功能：包含"开发/实现/添加/新增" → 完整流程
- Bug修复：包含"修复/Bug/问题/错误" → Bug分析→修复→回归测试
- 架构优化：包含"优化/重构/性能" → 性能分析→优化→性能测试
- 需求变更：包含"修改/变更/调整" → 影响分析→变更→回归测试

## 共享文档机制

**核心理念：一次产出，多次使用，避免重复劳动。**

### 共享目录结构

```
.cache/shared/
├── requirements/       # 需求文档（PM产出）
├── architecture/       # 架构设计（Architect产出）
├── api-design/         # API设计（Architect/Backend产出）
├── test-reports/       # 测试报告（Tester产出）
├── ui-review/          # UI审核报告（UI Designer产出）
├── code-review/        # 代码审查报告（Code Reviewer产出）
├── repo-map.md         # 仓库地图（全局项目结构，初始化时生成）
├── repo-index.json     # 结构化仓库索引（模块 / 文件 / 入口）
├── workflow-state.json # 当前工作流状态
├── workflow-runs.jsonl # 工作流事件流
└── SHARED_INDEX.md     # 总索引
```

### 文档生命周期

1. **创建**：技能产出文档 → 保存到共享目录 → 更新索引 → 通知团队
2. **使用**：查看索引 → 找到文档 → 读取内容 → 基于文档执行任务
3. **更新**：读取现有文档 → 更新内容 → 保存 → 通知变更

## Runtime 与恢复

当任务通过 `/0-emperor` 或 `/0-scrum-master` 进入自动编排时，当前仓库已经提供真实的 shell runtime：

```bash
sh skills/runtime/bin/workflow.sh start --mode=imperial --request="..."
sh skills/runtime/bin/workflow.sh status --json
sh skills/runtime/bin/workflow.sh resume --message="继续执行"
sh skills/runtime/bin/workflow.sh approve --message="步骤通过"
sh skills/runtime/bin/workflow.sh reject --reason="需要补充"
sh skills/runtime/bin/workflow.sh abort --message="终止流程"
```

运行时事实源：

- `.cache/shared/workflow-state.json`
- `.cache/shared/workflow-runs.jsonl`
- `.cache/shared/workflow-runtime/`

如果项目已经完成 `setup.sh --project-root=...`，执行类步骤会在 runtime 中自动接入 `.harness/bin/harness-check.sh` → `harness-fix.sh` → 再检查 的回环。

## 团队协作模式

### 作为团队成员的标准流程

1. 读取项目配置（PROJECT_CONFIG.md）
2. 读取共享文档（需求/架构/API设计等）
3. 读取编码规范（开发类技能）
4. 执行分配的任务
5. 保存产出到共享目录
6. 进行质量自检（开发类技能）
7. 遇到问题时报告给Scrum Master

### 主动协作原则

**每个技能都应主动识别协作机会，而不是被动等待分配：**

- 产品经理：需求变更时主动通知相关技能，验收测试时主动参与
- 架构师：新需求时主动评估架构影响，开发遇到技术难题时主动指导
- 后端开发：前端需要API时主动提供文档，发现性能问题时主动优化
- 前端开发：后端提供API后主动集成测试，UI设计稿出来后主动实现
- 测试工程师：开发完成后主动介入测试，Bug修复后主动验证
- Bug处理：用户报告错误时主动分析分类，协调修复流程

### 代码质量自检（开发类技能）

**后端：** 编码规范✓ 单元测试覆盖率≥80%✓ DDD分层✓ RESTful✓ 无安全漏洞✓
**前端：** 编码规范✓ 组件测试✓ 架构设计✓ Nielsen可用性✓ 无性能问题✓

## 双模式工作流

**本项目支持两种工作模式，根据任务复杂度选择：**

### 模式 A：敏捷团队模式（默认）

```
Scrum Master → PM/Architect/Designer 并行规划 → Dev/DevOps 并行执行 → Code Review → 提交
```

- 入口：`/0-scrum-master`
- 适合：小任务、Bug 修复、快速迭代、信任度高的场景
- 特点：扁平化协作，Scrum Master 自由协调各技能

### 模式 B：三省六部模式

```
👑 皇上(下旨) → 🤴 太子(分拣) → 📜 中书省(规划) → 🔍 门下省(审核) → 📮 尚书省(派发) → 六部(执行) → 🔍 门下省(验收) → 📜 回奏
```

- 入口：`/0-emperor`（皇上下旨）
- 适合：重要功能、架构变更、需要质量保障、多人协作的场景
- 特点：分权制衡，全流程审核，制度性质量门禁

### 模式选择规则

| 任务类型 | 推荐模式 | 原因 |
|---|---|---|
| Bug 修复 | 敏捷 | 快速响应，无需层层审核 |
| 小功能改动 | 敏捷 | 效率优先 |
| 新功能开发 | 三省六部 | 需要需求审核 + 架构审核 + 代码审核 |
| 架构变更 | 三省六部 | 影响面大，需要门下省把关 |
| 重构优化 | 三省六部 | 需要架构审核确保不破坏现有功能 |
| 文档编写 | 敏捷 | 无需代码审核 |

### 用户可手动指定模式

- 用户说"用三省六部模式"或"走审核流程" → 三省六部模式
- 用户说"快速处理"或"简单改一下" → 敏捷模式
- 未指定时，Scrum Master 根据任务复杂度自动推荐

## 敏捷仪式（简要）

| 仪式 | 时间 | 目标 |
|------|------|------|
| 迭代规划会 | 迭代第1天 | 确定本迭代工作，任务拆解和估算 |

| 迭代评审会 | 迭代最后一天 | 展示成果，收集反馈 |
| 迭代回顾会 | 迭代最后一天 | 反思过程，持续改进 |
