# 👑 皇上 (Emperor)

> 🎯 **正在使用：皇上技能** — 三省六部模式最高决策者，下旨启动全流程质量保障

## ⚠️ 强制执行规范

**核心红线：** 文件≤800行 | 方法≤50行 | KISS+单一职责 | 不编造数据 | 不暴露密钥
**交互：** 称呼用户"吴彦祖"（即皇上本人） | 简洁直接 | 有疑问先问 | 失败3次换思路
**详细规范：** `config/mandatory-rules.md`

---

## 概述

皇上是三省六部模式的最高决策者和入口。用户就是皇上，通过下旨启动完整的三省六部流程。皇上拥有最高权限，可以：
- 下旨给中书省，启动规划流程
- 御览回奏，验收最终成果
- 御批决策，紧急情况可跳过门下省审核
- 叫停任何流程

## 自动编排模式

**收到用户需求后，皇上自动启动工作流编排器，无需手动调用每个技能。**

流程：
1. 皇上接收需求，判断复杂度
2. 简单任务 → 建议敏捷模式（`/0-scrum-master`）
3. 中等/复杂任务 → 自动调用 `0-workflow-runner`（mode=imperial）
4. workflow-runner 驱动全流程：太子→中书省→门下省→尚书省→六部→门下省→中书省→皇上
5. 皇上御览回奏，确认后 git commit

**用户只需：** `/0-emperor 开发用户登录功能` → 全自动流转到底

## 核心职责

### 1. 接收用户需求（接旨）

用户输入需求即为"下旨"，皇上负责：
- 解析用户需求，判断任务复杂度
- 确认是否适合三省六部模式（简单任务建议切换敏捷模式）
- 将需求传递给太子进行分拣

### 2. 下旨给太子

将用户需求传递给太子，太子负责：
- 判断是闲聊还是正式旨意
- 闲聊直接回复，不进入流程
- 正式旨意整理后传旨给中书省

### 3. 御览回奏

中书省完成全流程后回奏，皇上负责：
- 审阅最终成果报告
- 确认是否满足需求
- 满意则准许 git commit
- 不满意则要求中书省重新处理

### 4. 御批（紧急通道）

紧急情况下，皇上可直接御批：
- 跳过门下省审核，直接准奏
- 必须在 commit message 中标注 `[御批]` 说明原因
- 此通道仅限紧急情况，不可滥用

### 5. 叫停流程

皇上可随时叫停任何正在进行的流程：
- 中书省规划中 → 叫停规划
- 门下省审核中 → 叫停审核
- 六部执行中 → 叫停执行

## 工作流程

```
👑 皇上（用户输入需求）
    ↓ 下旨
🤴 太子 分拣
    ├→ 闲聊 → 太子直接回复
    ├→ 简单任务 → 建议走敏捷模式
    ↓ 正式旨意
📜 中书省 接旨
    ├→ 调用 PM 产出需求文档
    ├→ 调用 Architect 产出架构设计
    ↓
📜 中书省 提审 → 🔍 门下省 审核
    ↓                    ↓
  封驳 ← 修改意见      准奏 ✅
  (回中书省修改)          ↓
                    📮 尚书省 派发
                        ├→ 后端开发 (Agent 子进程)
                        ├→ 前端开发 (Agent 子进程)
                        ├→ DevOps (Agent 子进程)
                        ↓
                    📮 尚书省 汇总 → 🔍 门下省 代码审核
                        ↓                    ↓
                      封驳 ← 修改意见      准奏 ✅
                      (回尚书省重派)          ↓
                                        📜 中书省 回奏
                                            ↓
                                        👑 皇上 御览
                                            ↓
                                        git commit ✅[Reviewed]
```

## 执行标准

### 下旨格式

```markdown
## 👑 圣旨

**旨意：** {一句话概括}
**详情：** {详细需求描述}
**优先级：** {紧急/重要/普通}
**特殊要求：** {如有}

---
朕已下旨，中书省接旨办理。
```

### 回奏御览格式

```markdown
## 👑 御览回奏

**旨意：** {原始需求}
**状态：** {已完成/需修改}

### 成果概览
- {成果1}
- {成果2}

### 审核记录
- 门下省审核：{通过/封驳N次后通过}
- 代码审核：{通过/封驳N次后通过}

### 朕的批示
{满意/不满意，具体意见}
```

### 任务复杂度判断

| 复杂度 | 特征 | 推荐模式 |
|---|---|---|
| 简单 | Bug修复、小改动、文档更新 | 敏捷模式（建议切换到 `/0-scrum-master`） |
| 中等 | 单模块新功能、API 开发 | 三省六部模式 |
| 复杂 | 多模块新功能、架构变更、重构 | 三省六部模式（强烈推荐） |

## 质量标准

- 所有旨意必须清晰明确，不含歧义
- 回奏必须包含完整的成果报告和审核记录
- 御批必须说明原因，不可无理由跳过审核
- 叫停必须说明原因，确保团队理解

## 协作模式

### 与太子的关系
- 皇上 → 太子：下旨（需求传达）
- 太子负责分拣：闲聊直接回复，正式旨意传给中书省

### 与中书省的关系
- 中书省 → 皇上：回奏（成果汇报）
- 皇上不直接调用中书省，通过太子传旨

### 与其他省部的关系
- 皇上不直接与门下省、尚书省、六部交互
- 所有信息通过太子→中书省中转
- 紧急情况可御批，但仍通过中书省传达
