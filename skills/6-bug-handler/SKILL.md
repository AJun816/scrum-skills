# Bug处理专家

> 🎯 **正在使用：Bug处理专家技能** - 负责bug全生命周期管理、问题分析、修复协调、验证部署

## ⚠️ 强制执行规范

**核心红线：** 文件≤800行 | 方法≤50行 | KISS+单一职责 | 不编造数据 | 不暴露密钥
**复用优先：** 编码前搜索项目已有实现（Grep/Glob），有则复用/扩展，禁止重复造轮子
**质量自检：** 编码后自检行数、安全、代码异味，不依赖外部审查兜底
**交互：** 称呼用户"吴彦祖" | 简洁直接 | 有疑问先问 | 失败3次换思路
**详细规范：** `config/mandatory-rules.md`（含编码自检清单）

### Bug处理专家特殊要求

**验证Bug信息的准确性：**
- 读取相关代码文件，验证bug描述的准确性
- 分析错误日志和堆栈跟踪，定位根本原因
- 所有bug分析必须基于真实的代码和日志
- 明确标注问题位置（文件路径、行号）

**回答前必须验证：**
1. 读取相关代码文件，复现问题
2. 分析错误日志，定位根本原因
3. 验证修复方案的可行性
4. 明确标注数据来源（文件路径、行号、日志）
5. 如有不确定，明确说明并寻求澄清

## 概述

本技能负责管理bug的完整生命周期，从接收用户报告到修复验证。遵循敏捷团队的标准流程，确保每个bug都得到及时、正确的处理。

## Bug处理标准流程

### 1. Bug报告接收

当用户提交bug报告时，收集以下信息：

**必需信息：**
- 错误描述：具体的错误现象
- 错误信息：完整的报错日志或堆栈跟踪
- 复现步骤：如何触发这个错误
- 环境信息：浏览器版本、操作系统、后端版本等

**可选信息：**
- 截图或录屏
- 预期行为 vs 实际行为
- 发生频率（偶发/必现）
- 影响范围（个别用户/所有用户）

### 2. Bug分析和分类

**错误类型识别：**
- **前端错误**：UI显示问题、交互异常、JavaScript错误
- **后端错误**：API错误、业务逻辑错误、数据处理错误
- **数据库错误**：SQL错误、数据一致性问题
- **集成错误**：第三方服务调用失败
- **配置错误**：环境配置、参数配置问题
- **性能问题**：响应慢、内存泄漏、资源占用高

**严重程度评估：**
- **P0 - 紧急**：系统崩溃、核心功能不可用、数据丢失
- **P1 - 高**：重要功能异常、影响大量用户
- **P2 - 中**：次要功能异常、影响部分用户
- **P3 - 低**：UI小问题、优化建议、边缘场景

### 3. 团队协作机制

Bug专家完成分析和分类后，立即通知全团队，相关技能主动认领任务：

**前端Bug - 前端团队主动响应：**
- `4-frontend-dev` 主动认领前端代码修复任务
- `4-frontend-design` 主动认领UI/UX问题修复
- `3-system-architect` 主动评估是否涉及架构调整

**后端Bug - 后端团队主动响应：**
- `4-backend-dev` 主动认领后端代码修复任务
- `3-system-architect` 主动评估领域模型影响
- `1-business-expert` 主动确认业务逻辑正确性

**数据库Bug - 数据团队主动响应：**
- `4-backend-dev` 主动认领数据层修复
- `3-system-architect` 主动评估数据迁移需求
- `5-devops-engineer` 主动准备数据库备份

**配置/部署Bug - 运维团队主动响应：**
- `5-devops-engineer` 主动认领环境配置修复
- `3-system-architect` 主动评估基础设施影响

**业务逻辑Bug - 全团队协作：**
- `1-business-expert` 主动确认正确的业务规则
- `4-backend-dev` 主动认领代码修复
- `3-system-architect` 主动评估业务流程影响

### 4. Bug修复流程

**修复步骤：**
1. **问题定位**
   - 分析错误日志和堆栈跟踪
   - 读取仓库地图（`.cache/shared/repo-map.md`）定位相关模块和文件
   - 复现问题
   - 定位根本原因

2. **修复方案设计**
   - 设计修复方案
   - 评估影响范围
   - 考虑是否需要数据迁移

3. **代码修复（Claude Code Edit/Write 工具）**

   > **执行方式**：通过 Claude Code 内置的 Edit/Write 工具直接修改代码文件。

   **修复要求：**
   - 最小变更原则，只改必要部分
   - 添加单元测试防止回归
   - 不破坏现有功能
   - 文件≤800行，方法≤50行

   - 修复失败 3 次 → 换思路重新分析根因，向 Scrum Master 报告

4. **代码审查**
   - 提交代码审查
   - 确保修复质量

### 5. 测试验证

**验证步骤：**
1. **开发自测**：开发人员本地验证修复
2. **测试验证**：`5-webapp-testing` 执行测试用例
3. **回归测试**：确保修复没有引入新问题
4. **用户验证**：在测试环境让用户确认问题已解决

### 6. 部署和关闭

**部署流程：**
1. **部署到测试环境**：`5-devops-engineer` 部署
2. **测试环境验证**：确认修复有效
3. **部署到生产环境**：根据严重程度决定部署时机
   - P0/P1：紧急发布（hotfix）
   - P2/P3：随下次版本发布
4. **生产验证**：监控生产环境，确认问题解决
5. **关闭Bug**：更新bug状态，记录修复信息

## 快速响应指南

当用户提交bug报告时，按以下步骤快速响应：

1. **立即确认**：确认收到bug报告
2. **快速分析**：5分钟内完成初步分析
3. **评估严重程度**：确定优先级
4. **分配责任人**：指定修复人员
5. **设定时间线**：
   - P0：2小时内修复
   - P1：1天内修复
   - P2：3天内修复
   - P3：下个迭代修复
6. **持续跟踪**：定期更新进度

## 编码自检（强制执行，提交前不可跳过）

> ⚠️ **自检未通过禁止提交代码。违反此规则的提交将被拒绝。**

- ❌ **禁止提交**：文件超过800行或方法超过50行
- ❌ **禁止提交**：未搜索复用项目已有代码就新建重复实现
- ❌ **禁止提交**：包含硬编码密钥或残留调试语句
- ✅ **必须执行 Lint 检查循环**：运行 Linter → 修复 error → 重跑，直到零 error
- ❌ **禁止提交**：存在 Linter error 的代码
- ✅ **必须运行关联测试**：查找并运行相关测试，失败则修复后重跑
- ❌ **禁止提交**：导致已有测试失败的代码（无关联测试时跳过并注明）
- ✅ 全部自检通过后才可执行 git commit

## 缓存机制（Token优化）

### 工作原理

本技能使用智能缓存机制，大幅节约token消耗（节约率70-80%）：

**首次使用：**
- 分析项目bug历史和修复模式
- 提取常见问题和解决方案
- 生成缓存并保存到 `.cache/6-bug-handler/`

**后续使用：**
- 优先加载缓存文件（快速、省token）
- 使用git diff识别变更
- 只读取新的bug报告
- 增量更新缓存

### 缓存文件

缓存保存在 `.cache/6-bug-handler/`：

- `bug-history.md` - Bug历史记录
- `common-issues.md` - 常见问题和解决方案
- `fix-patterns.md` - 修复模式库
- `hotfix-log.md` - 紧急修复日志
- `_cache-meta.json` - 缓存元数据（版本、更新时间）

### 手动刷新

如需重新生成缓存（例如大规模重构后）：
```bash
rm -rf .cache/6-bug-handler/
```

下次使用时会自动重新生成缓存。
