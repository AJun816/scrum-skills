# 用户故事编写详细指南

## 概述

本文档详细说明如何编写高质量的用户故事，包括故事点估算、优先级定义、验收标准编写和完整示例。

## 用户故事格式

### 基本格式

```
作为 [用户角色]
我想要 [功能描述]
以便 [业务价值]

故事点：[1/2/3/5/8/13/21]（斐波那契数列）
优先级：[P0/P1/P2/P3]
```

### 验收标准（Given-When-Then）

```
Given [前置条件]
When [执行操作]
Then [预期结果]
And [额外结果]（可选）
```

## 故事点估算指南

### 斐波那契数列说明

使用斐波那契数列（1, 2, 3, 5, 8, 13, 21）进行故事点估算，数字越大表示复杂度越高。

### 详细估算标准

#### 1 Point - 极简单

**复杂度：** 极简单
**描述：** 几乎不需要思考，直接实现
**时间估算：** < 2小时

**典型示例：**
- 修改文案
- 调整样式
- 简单配置修改
- 修改常量值
- 调整布局间距

**特征：**
- 无需设计
- 无需测试（或极简单测试）
- 无技术难点
- 无业务逻辑

#### 2 Points - 简单

**复杂度：** 简单
**描述：** 清晰明确，无技术难点
**时间估算：** 2-4小时

**典型示例：**
- 添加简单表单字段
- 实现简单的CRUD接口
- 添加简单的前端组件
- 简单的数据验证
- 简单的页面跳转

**特征：**
- 需求清晰
- 实现方案明确
- 少量测试
- 无复杂业务逻辑

#### 3 Points - 中等偏简单

**复杂度：** 中等偏简单
**描述：** 需要一定思考，但方案明确
**时间估算：** 4-8小时

**典型示例：**
- 实现带验证的表单
- 实现简单的业务逻辑
- 集成第三方API（文档完善）
- 实现简单的数据统计
- 实现简单的权限控制

**特征：**
- 需要一定设计
- 需要编写测试
- 有一定业务逻辑
- 可能涉及多个模块

#### 5 Points - 中等

**复杂度：** 中等
**描述：** 需要设计和思考，有一定复杂度
**时间估算：** 1-2天

**典型示例：**
- 实现复杂的业务流程
- 设计和实现新的数据模型
- 实现带权限控制的功能
- 实现复杂的表单验证
- 实现数据导入导出

**特征：**
- 需要详细设计
- 需要完整测试
- 涉及多个模块
- 有复杂业务逻辑

#### 8 Points - 复杂

**复杂度：** 复杂
**描述：** 需要深入设计，涉及多个模块
**时间估算：** 2-3天

**典型示例：**
- 实现支付流程
- 实现复杂的数据统计和报表
- 重构核心模块
- 实现工作流引擎
- 实现消息推送系统

**特征：**
- 需要架构设计
- 需要全面测试
- 涉及多个系统
- 有复杂的技术挑战

**建议：** 考虑拆分为多个小故事

#### 13 Points - 非常复杂

**复杂度：** 非常复杂
**描述：** 需要详细设计，涉及多个系统
**时间估算：** 3-5天

**典型示例：**
- 实现订单系统
- 实现权限管理系统
- 实现复杂的工作流引擎
- 实现数据同步系统
- 实现搜索引擎集成

**特征：**
- 需要完整架构设计
- 需要全面测试和性能测试
- 涉及多个系统集成
- 有重大技术风险

**强烈建议：** 拆分为多个小故事

#### 21 Points - 极其复杂（史诗级）

**复杂度：** 极其复杂
**描述：** 史诗级故事，必须拆分
**时间估算：** > 1周

**典型示例：**
- 实现完整的电商平台
- 实现完整的CRM系统
- 实现完整的ERP系统
- 大规模系统重构

**特征：**
- 需要完整的系统设计
- 涉及多个子系统
- 需要长期规划
- 有重大业务和技术风险

**必须：** 拆分为多个小故事，不应直接实现

## 优先级定义

### P0 - 紧急且重要

**名称：** 紧急且重要
**描述：** 系统崩溃、数据丢失、安全漏洞等
**响应时间：** 立即处理
**颜色标识：** 🔴 红色
**SLA：** 2小时内响应，24小时内解决

**典型示例：**
- 生产环境系统崩溃
- 严重安全漏洞
- 数据丢失或损坏
- 核心功能完全不可用
- 支付系统故障
- 用户无法登录

**处理原则：**
- 立即停止当前工作
- 组建应急团队
- 优先级最高
- 需要实时汇报进度

### P1 - 重要但不紧急

**名称：** 重要但不紧急
**描述：** 核心功能、重要需求、影响大量用户
**响应时间：** 本迭代完成
**颜色标识：** 🟠 橙色
**SLA：** 当前迭代内完成

**典型示例：**
- 核心业务功能开发
- 影响大量用户的功能
- 重要的性能优化
- 关键的用户体验改进
- 重要的业务流程优化
- 关键的集成功能

**处理原则：**
- 纳入当前迭代计划
- 优先级高于P2/P3
- 需要充分测试
- 需要详细文档

### P2 - 一般重要

**名称：** 一般重要
**描述：** 常规功能、优化改进、影响部分用户
**响应时间：** 近期迭代完成
**颜色标识：** 🟡 黄色
**SLA：** 1-2个迭代内完成

**典型示例：**
- 常规功能开发
- 一般性能优化
- 次要功能改进
- 影响部分用户的问题
- 用户体验优化
- 功能增强

**处理原则：**
- 根据资源情况安排
- 可以延后到下个迭代
- 需要基本测试
- 需要基本文档

### P3 - 可选

**名称：** 可选
**描述：** 锦上添花、技术债务、长期规划
**响应时间：** 有空再做
**颜色标识：** 🟢 绿色
**SLA：** 根据资源情况安排

**典型示例：**
- Nice to have功能
- 技术债务偿还
- 代码重构
- 文档完善
- 性能微调
- 界面美化

**处理原则：**
- 资源充足时处理
- 可以长期积压
- 可以取消
- 测试和文档可选

## 完整示例

### 示例1：导出活动数据报表

```markdown
## 用户故事 #1：导出活动数据报表

### 基本信息

- **故事ID：** US-001
- **创建日期：** 2024-02-13
- **创建人：** Product Manager
- **优先级：** P1（重要但不紧急）
- **故事点：** 5（中等复杂度）
- **状态：** 待办
- **所属迭代：** Sprint 3

### 用户故事

作为 营销人员
我想要 导出活动数据报表
以便 分析活动效果并优化投放策略

### 验收标准

1. **场景1：成功导出报表**
   - Given 用户已登录系统
   - And 用户在活动列表页面
   - When 用户点击"导出报表"按钮
   - Then 系统生成 Excel 文件并开始下载
   - And 文件名格式为"活动报表_{日期}.xlsx"
   - And 文件包含所有活动数据（活动名称、开始时间、结束时间、参与人数、转化率）

2. **场景2：无数据时的提示**
   - Given 用户已登录系统
   - And 当前没有任何活动数据
   - When 用户点击"导出报表"按钮
   - Then 系统显示提示"暂无数据可导出"
   - And 不生成文件

3. **场景3：导出失败的处理**
   - Given 用户已登录系统
   - And 系统服务异常
   - When 用户点击"导出报表"按钮
   - Then 系统显示错误提示"导出失败，请稍后重试"
   - And 记录错误日志

### 技术实现要点

**后端：**
- API端点：GET /api/v1/activities/export
- 数据模型：Activity, ActivityReport
- 业务逻辑：查询活动数据，生成Excel文件，返回文件流

**前端：**
- 页面/组件：ActivityList.vue
- 交互逻辑：点击按钮触发下载
- 状态管理：loading状态管理

### 依赖关系

- **依赖于：** US-000（活动列表查询功能）
- **被依赖：** 无

### 测试要点

- [x] 单元测试：测试报表生成逻辑
- [x] 集成测试：测试API接口
- [x] UI测试：测试下载流程
- [ ] 性能测试：测试大数据量导出
- [ ] 安全测试：测试权限控制

### 备注

- Excel文件使用Apache POI生成
- 支持最多导出10000条数据
- 超过10000条数据需要分批导出
```

### 示例2：用户登录功能

```markdown
## 用户故事 #2：用户登录功能

### 基本信息

- **故事ID：** US-002
- **创建日期：** 2024-02-13
- **创建人：** Product Manager
- **优先级：** P0（紧急且重要）
- **故事点：** 3（中等偏简单）
- **状态：** 进行中
- **所属迭代：** Sprint 1

### 用户故事

作为 系统用户
我想要 使用用户名和密码登录系统
以便 访问系统功能

### 验收标准

1. **场景1：成功登录**
   - Given 用户在登录页面
   - And 用户输入正确的用户名和密码
   - When 用户点击"登录"按钮
   - Then 系统验证用户身份
   - And 跳转到首页
   - And 显示用户信息

2. **场景2：登录失败**
   - Given 用户在登录页面
   - And 用户输入错误的用户名或密码
   - When 用户点击"登录"按钮
   - Then 系统显示错误提示"用户名或密码错误"
   - And 保持在登录页面

3. **场景3：记住登录状态**
   - Given 用户成功登录
   - And 用户勾选"记住我"选项
   - When 用户关闭浏览器后重新打开
   - Then 用户仍然保持登录状态

### 技术实现要点

**后端：**
- API端点：POST /api/v1/auth/login
- 数据模型：User, LoginRequest, LoginResponse
- 业务逻辑：验证用户名密码，生成JWT token

**前端：**
- 页面/组件：Login.vue
- 交互逻辑：表单验证，登录请求，token存储
- 状态管理：Pinia存储用户信息和token

### 依赖关系

- **依赖于：** 无
- **被依赖：** US-003（用户权限管理）

### 测试要点

- [x] 单元测试：测试登录逻辑
- [x] 集成测试：测试API接口
- [x] UI测试：测试登录流程
- [x] 安全测试：测试密码加密和token安全

### 备注

- 密码使用BCrypt加密
- Token有效期为7天
- 支持记住登录状态（30天）
```

## 最佳实践

### 编写用户故事的原则

1. **独立性（Independent）**
   - 故事之间尽量独立
   - 减少依赖关系
   - 可以独立开发和测试

2. **可协商（Negotiable）**
   - 故事是讨论的起点，不是合同
   - 细节可以在实现过程中调整
   - 保持灵活性

3. **有价值（Valuable）**
   - 每个故事都要为用户创造价值
   - 避免纯技术故事
   - 关注业务目标

4. **可估算（Estimable）**
   - 故事要足够清晰，可以估算工作量
   - 如果无法估算，说明需要进一步澄清
   - 使用相对估算（故事点）

5. **小（Small）**
   - 故事要足够小，可以在一个迭代内完成
   - 大故事要拆分
   - 目标：1-5个故事点

6. **可测试（Testable）**
   - 每个故事都要有明确的验收标准
   - 验收标准要可测试
   - 使用Given-When-Then格式

### 常见错误和避免方法

**错误1：故事太大**
- ❌ "实现用户管理系统"（太大，无法估算）
- ✅ "实现用户注册功能"（具体，可估算）

**错误2：缺少业务价值**
- ❌ "创建User表"（纯技术，无业务价值）
- ✅ "作为管理员，我想要管理用户信息，以便控制系统访问权限"

**错误3：验收标准不明确**
- ❌ "系统应该快速响应"（不可测试）
- ✅ "系统响应时间应该在2秒内"（可测试）

**错误4：技术实现细节过多**
- ❌ "使用Redis缓存用户数据"（技术细节）
- ✅ "提高用户信息查询性能"（业务目标）

## 总结

编写高质量的用户故事需要：
1. ✅ 使用标准格式（As a... I want... So that...）
2. ✅ 合理估算故事点（1-21）
3. ✅ 明确优先级（P0-P3）
4. ✅ 编写清晰的验收标准（Given-When-Then）
5. ✅ 遵循INVEST原则
6. ✅ 关注业务价值，而非技术实现

好的用户故事是团队协作的基础，是敏捷开发成功的关键！
