# 全自动化敏捷团队工作流程

**本文件定义0-scrum-master的全自动化工作流程**

## 核心原则

1. **全自动化**：用户只需描述需求，Scrum Master自动完成所有协调工作
2. **使用TeamCreate + Task工具**：创建团队，管理任务，协调协作
3. **代码质量优先**：自动进行代码审查、测试、质量检查
4. **通用可配置**：适用于任何项目，业务场景在PROJECT_CONFIG.md中自动追踪
5. **全程透明**：每个角色运行时自我介绍，实时显示进度

## 标准敏捷业务流程

当用户发送一个任务时，0-scrum-master自动执行以下流程：

```
用户任务
  ↓
1. 需求分析（Product Manager）
  ↓
2. 用户故事（Product Manager）
  ↓
3. 架构设计（System Architect）
  ↓
4. 开发（Backend Dev + Frontend Dev + UI Designer）
  ↓
5. 测试（Tester）
  ↓
6. 输出测试结果md文件
```

## 任务类型识别机制

### 新功能开发

**识别特征：**
- 用户描述包含"开发"、"实现"、"添加"、"新增"等关键词
- 涉及新的业务功能

**工作流程：**
1. Product Manager：需求分析 + 用户故事
2. System Architect：架构设计
3. Backend Developer：后端开发
4. Frontend Developer：前端开发
5. UI Designer：UI审核
6. Tester：测试

### Bug修复

**识别特征：**
- 用户描述包含"修复"、"Bug"、"问题"、"错误"等关键词

**工作流程：**
1. Bug Handler：Bug分析
2. System Architect：修复方案设计
3. Backend/Frontend Developer：修复实现
4. Tester：回归测试

### 架构优化

**识别特征：**
- 用户描述包含"优化"、"重构"、"性能"、"架构"等关键词

**工作流程：**
1. System Architect：性能分析 + 优化方案
2. Backend/Frontend Developer：优化实现
3. Tester：性能测试

### 需求变更

**识别特征：**
- 用户描述包含"修改"、"变更"、"调整"等关键词

**工作流程：**
1. Product Manager：变更影响分析
2. System Architect：变更设计
3. Backend/Frontend Developer：变更实现
4. Tester：回归测试

## 敏捷仪式执行

### 迭代周期

**标准迭代周期：** 1-2周（可根据项目需求调整）

```yaml

  duration: "2周"  # 1周或2周
  start_day: "周一"
  end_day: "周五"
```

## 迭代模式

### 迭代流程图

```
迭代开始
  ↓
迭代规划会（Day 1）
  ↓
每日站会（Day 1-10）
  ↓
Backlog梳理（Day 5）
  ↓
迭代评审会（Day 10）
  ↓
迭代回顾会（Day 10）
  ↓
迭代结束
  ↓
下一迭代开始
```

### 迭代节奏

**2周迭代示例：**

| 时间 | 活动 | 时长 | 参与者 |
|------|------|------|--------|
| 周一上午 | 迭代规划会 | 3小时 | 全体 |
| 周一-周五 | 每日站会 | 15分钟/天 | 全体 |
| 周一-周五 | 开发工作 | - | 开发团队 |
| 周三下午 | Backlog梳理 | 2小时 | PM+架构师+部分开发 |
| 周五上午 | 迭代评审会 | 2小时 | 全体+利益相关者 |
| 周五下午 | 迭代回顾会 | 1.5小时 | 全体 |

### 速率跟踪机制

#### 速率定义

**速率（Velocity）：** 团队在一个迭代中完成的故事点总数

#### 速率计算

```yaml
velocity_calculation:
  formula: "完成的故事点总数 / 迭代数"

  example:
    sprint_1: 23点
    sprint_2: 27点
    sprint_3: 25点
    average_velocity: 25点
```

#### 速率跟踪表

```markdown
| 迭代 | 承诺故事点 | 完成故事点 | 速率 | 完成率 | 趋势 |
|------|-----------|-----------|------|--------|------|
| Sprint 1 | 25 | 23 | 23 | 92% | - |
| Sprint 2 | 25 | 27 | 27 | 108% | ↑ |
| Sprint 3 | 27 | 25 | 25 | 93% | ↓ |
| Sprint 4 | 25 | 26 | 26 | 104% | ↑ |
| **平均** | **25.5** | **25.3** | **25.3** | **99%** | **稳定** |
```

#### 速率使用

**迭代规划时：**
- 参考历史平均速率
- 考虑团队可用性（假期、培训等）
- 预留10-20%缓冲

**示例：**
```
历史平均速率：25点
本迭代可用性：90%（1人请假）
调整后速率：25 × 0.9 = 22.5点
承诺故事点：20-23点（预留缓冲）
```

#### 燃尽图分析

**健康状态：**
- ✅ **按计划**：实际线接近理想线
- ⚠️ **有风险**：实际线高于理想线
- ❌ **落后**：实际线远高于理想线
- 🎉 **超前**：实际线低于理想线

**示例分析：**
```markdown
## 燃尽图分析 - Sprint 4

**当前状态：** ⚠️ 有风险

**数据：**
- 迭代天数：10天
- 当前天数：Day 7
- 剩余故事点：12点
- 理想剩余：7.5点
- 差距：+4.5点

**原因分析：**
- Day 4-5进度停滞（技术障碍）
- Day 6-7恢复正常

**应对措施：**
1. 移除技术障碍（已完成）
2. 考虑降低承诺（移除低优先级任务）
3. 增加结对编程加速开发

**预测：**
- 按当前速率：预计完成20点（80%）
- 需要加速：每天完成4点才能完成目标
```

## 总结

通过全自动化工作流程和完整的敏捷仪式，技能组实现：

1. **全自动化**：用户只需描述需求，团队自动完成所有工作
2. **标准流程**：遵循敏捷团队的标准业务流程
3. **角色明确**：每个角色自我介绍，职责清晰
4. **代码质量**：自动检查、审查、测试，确保质量
5. **高效协作**：并行执行，智能协调，快速交付
6. **通用可配置**：适用于任何项目，自动追踪业务场景
7. **敏捷仪式**：完整的敏捷仪式体系，确保流程规范
8. **迭代管理**：清晰的迭代规划和回顾机制
9. **数据驱动**：速率跟踪和燃尽图，可视化进度
10. **持续改进**：定期回顾，不断优化流程

**让技能组像真正的敏捷团队一样，高效、专业、自动化地完成任务。**
