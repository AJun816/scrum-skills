# 敏捷开发实践指南

## 敏捷核心原则

### 1. 迭代开发
- 短周期迭代（1-2周）
- 每个迭代交付可用功能
- 持续集成和部署

### 2. 用户故事驱动
- 以用户价值为中心
- 小而独立的故事
- 可测试的验收标准

### 3. 团队协作
- 每日站会同步进度
- 迭代计划会议
- 回顾会议持续改进

## 用户故事编写

### 标准格式
```
作为 [用户角色]
我想要 [功能描述]
以便 [业务价值]
```

### 示例
```
作为 营销人员
我想要 导出活动数据报表
以便 分析活动效果并优化投放策略
```

### INVEST 原则
- **I**ndependent（独立的）：故事之间相互独立
- **N**egotiable（可协商的）：细节可以讨论调整
- **V**aluable（有价值的）：对用户有明确价值
- **E**stimable（可估算的）：可以评估工作量
- **S**mall（小的）：足够小，可在一个迭代完成
- **T**estable（可测试的）：有明确的验收标准

## 验收标准定义

### Given-When-Then 格式
```
Given [前置条件]
When [执行操作]
Then [预期结果]
```

### 示例
```
Given 用户已登录系统
When 用户点击"导出报表"按钮
Then 系统生成 Excel 文件并开始下载
And 文件包含所有活动数据
And 文件格式符合规范
```

## 任务拆解原则

### 垂直切分
- 每个故事包含完整的功能切片
- 从前端到后端到数据库
- 可独立交付和测试

### 技术任务拆解
1. **后端任务**
   - 领域模型设计
   - API 接口实现
   - 数据库变更
   - 单元测试

2. **前端任务**
   - 页面组件开发
   - 状态管理
   - API 集成
   - 组件测试

3. **测试任务**
   - 测试用例编写
   - 功能测试
   - 集成测试
   - 验收测试

## 工作量估算

### 故事点估算
- 使用斐波那契数列：1, 2, 3, 5, 8, 13
- 相对估算，不是绝对时间
- 团队共同估算

### 估算参考
- 1 点：简单修改，几小时完成
- 2 点：小功能，半天到一天
- 3 点：中等功能，1-2 天
- 5 点：较复杂功能，2-3 天
- 8 点：复杂功能，需要拆分
- 13 点：太大，必须拆分

## 迭代流程

### 1. 迭代计划会议
- 评审产品待办列表
- 选择本迭代要完成的故事
- 拆解技术任务
- 估算工作量

### 2. 每日站会
- 昨天完成了什么
- 今天计划做什么
- 遇到什么阻碍

### 3. 迭代评审
- 演示完成的功能
- 收集反馈
- 验收故事

### 4. 迭代回顾
- 总结做得好的地方
- 识别改进点
- 制定行动计划

## 质量保证

### Definition of Done (DoD)
- 代码完成并通过评审
- 单元测试覆盖率达标
- 集成测试通过
- 文档更新完成
- 验收标准全部满足
- 部署到测试环境

### 持续集成
- 代码提交触发自动构建
- 自动运行测试
- 代码质量检查
- 快速反馈问题
